# 卡片角色看板與相關卡片（設計）

日期：2026-11-03。延伸自卡片概念圖卡的「全書概念地圖」（`docs` 內尚無獨立 spec，見 CLAUDE.md「卡片概念圖卡」）。

## 為什麼

使用者都在 Notion 上讀卡片，讀的時候遇到三個問題：

1. 每張卡的 📖 章名＋進度那行多餘，讀者看了不知道該有什麼反應。
2. `來源劃線ID` 對讀者沒有資訊。程式需要它（查重、回查書、做圖對回本地卡），所以保留，只在 Notion 隱藏。
3. 卡片之間有關聯，卻沒有呈現，也不確定閱讀順序。使用者的例子：〈危機處理應對：區分可控與不可控因素〉和〈50%法則：為自己的反應承擔全部責任〉（兩張都在《主控力》）。

使用者選擇看板的理由：**卡片本身就是地圖，比較直覺，也保有調整的彈性。**

## 目標與成功標準

在《主控力：全球領導力大師掌握人生的12個新策略》上實際跑完後，在 Notion 看得到：

1. 書頁「筆記圖」段是看板，分成主軸、支柱、案例三欄，同一欄依閱讀順序排列。
2. 〈危機處理應對〉與〈50%法則〉出現在彼此的「相關卡片」。
3. 這本書的卡片沒有 📖 那行；新產的卡也不再寫這行。
4. 手動改過閱讀順序、把卡拖到別欄、刪掉一條連結之後重跑工具：這些改動都還在，而且**完全不呼叫模型**。

全部書跑完時，單本失敗不影響其他書，失敗的書什麼都不寫，下次重跑會再試。

## 非目標

- 跨書連結、概念頁（`docs/KNOWLEDGE_SYSTEM_GAPS.md` B2、ZETTELKASTEN #3-3）。
- 前提／導向／對照這三種關係類型（試跑顯示方向不可靠，見下）。
- 在使用者手動建立的書頁上放看板。
- 補卡片的 cover／icon（另有 `tools/backfill_card_visuals.py`，看板在那之前就是純文字卡片）。
- 改動產卡與審核的提示詞。

## 反目標（做到就算失敗，即使功能能跑）

- 蓋掉使用者手動改過的任何內容，包括卡片內文、`狀態`、`品質分數`、角色、閱讀順序、連結。
- 刪掉使用者自己建立的 view。
- 模型失敗時把整本書壓平成全部「案例」還寫進 Notion。
- 為了看起來連得多而留下不可靠的連結：寧缺勿濫。

## 使用者已決定

| 項目 | 決定 |
|---|---|
| 📖 那行 | 新卡不寫；既有卡片一次清掉，清之前先預覽 |
| 全書地圖的呈現 | 依角色分欄的看板（考慮過可收合的大綱與 Mermaid 關係圖） |
| 同欄順序 | 程式先排好，使用者靠改數字微調（放棄自由拖動換序） |
| 卡片連結 | 一個「相關卡片」欄位，不分前提／導向／對照 |
| 來源劃線ID | 保留；使用者自己在 Notion 隱藏 |
| 新卡的順序 | 排在同一本書最後 |
| 現有 gallery | 由看板取代 |
| 範圍 | 所有書的卡片都填欄位；看板只放在同步自動建立的書頁 |

## 試跑證據（2026-11-03）

真實資料：《主控力》18 張卡，內容從 Notion 讀取，`gemma4:12b`，RTX 2070 SUPER 8GB，沿用現有 `build_book_map_prompt`（只讀不寫）。

| 試跑 | 結果 | 兩張例子卡 |
|---|---|---|
| 書中順序列出 | 203 秒，17 組連結 | 危機處理 → 50%法則 |
| 打亂順序列出 | 168 秒，12 組連結 | 50%法則 → 危機處理 |
| 打亂順序＋修改提示詞（要求比例、預覽 160 字） | 31 秒，JSON 壞掉，只解析出 1 張 | 沒連到 |

另有一次在載入模型時 CUDA 崩潰（`shared object initialization failed`），原因未查明，直接重跑就好。18 張卡的書中順序全部查得到。

由此得出的設計依據：

- **連結要過濾：** 兩次只共同出現 5 組，這 5 組都合理（迂迴↔直指核心、直指核心↔發掘目標、危機處理↔50%法則、深層提問↔發掘目標、改變視角↔提升溝通），其餘不一致。只測了一本書，樣本有限。
- **方向不可靠：** 同一組卡兩次方向相反，所以不分方向，先後交給閱讀順序。
- **`normalize_book_map` 有兩個 bug：**
  - 模型把「支柱」寫成「支撐」（打亂順序那次為主軸 3、支撐 9、案例 6），未知角色一律變案例，分布合理的結果被壓成幾乎全是案例。
  - 只定位到 1 張卡也算成功，其餘變案例，還會被快取。
- **提示詞先不改：** 修改版反而壞掉，原版至少兩次都成功。要改就要重測。

## 設計

### 1. 卡片盒新欄位

| 欄位 | 型別 | 說明 |
|---|---|---|
| `角色` | select，選項依序為 主軸、支柱、案例 | 看板分欄依據 |
| `閱讀順序` | number | 10、20、30…留間隔，要插到兩張中間只需打一個數字 |
| `相關卡片` | relation，指向卡片盒自己，**單一欄位**（`single_property`） | 雙向關係若用 `dual_property` 會變成兩個欄位 |

由新方法 `ensure_card_board_columns()` 建立，比照 `ensure_infographic_column()`：**不放進 `_ensure_schema`**，以免一般同步多建欄位。

現況（2026-11-03 查證）：實際的卡片盒只有 `標題`、`Tags`、`Key Word`、`來源`、`來源劃線ID`、`狀態`、`品質分數`、`Last edited time`，還沒有 `加工狀態`／`建立日期`／`上次回顧`／`做圖`，這批卡也沒有 cover 和 icon。`.env` 的 `ENABLE_ZETTELKASTEN_CARDS=false`，這台電腦也沒有 `cards_output/`。

### 2. 閱讀順序：不靠模型

用 `來源劃線ID` 查 `Bookmark`，以 `(spine 的 VolumeIndex, ChapterProgress)` 排序，第一張 10，之後每張加 10。試跑時的查法：`Bookmark.ContentID` 取 `!` 後最後一段（去掉 `#`）得檔名，對 `content`（`BookID = VolumeID` 且 `ContentType = 9`）的 `VolumeIndex`。

查不到位置的卡（手動建立、沒有 `KoboReader.sqlite`、ID 是原文雜湊）排最後，彼此依 `created_time`，並記 WARNING。

新卡：同一本書已有數字時，從目前最大值往上加 10（新卡之間依書中順序）。

### 3. 角色與連結：跑兩次模型

每本書呼叫兩次 `build_book_map`：第一次依書中順序列出卡片，第二次打亂。打亂要用從書名算出的固定種子（sha1，不可用內建 `hash()`），重跑才穩定。

卡片內容從 **Notion** 讀（標題＋頂層 paragraph），不是本地 JSON：這台電腦沒有本地 JSON，而且使用者會手動改卡片（例如〈全面視角〉內文就有「待修正的點」）。

合併規則（放 domain，純函式）：

- **連結：** 取兩次的交集，把每組視為不分方向的一對，不看關係類型。
- **角色：** 相同就用；不同取較低階（主軸 > 支柱 > 案例），沿用「不替沒把握的卡宣稱它是主軸」的原則。

失敗處理：每次呼叫最多試 2 次（涵蓋 CUDA 崩潰與 JSON 壞掉）。任一次最終失敗，這本書這輪什麼都不寫。

模型設定：新增 `OLLAMA_CARD_MAP_MODEL`，預設 `gemma4:12b`，**不退回 `OLLAMA_MODEL`**（`qwen3:4b` 實測全部標同一角色、關係亂串）。逾時用獨立的 `OLLAMA_CARD_MAP_TIMEOUT_SECONDS`，預設 600：現有的 300 秒離實測的 203 秒太近。模型沒開或沒下載時，在任何寫入之前就中止並說明原因。

### 4. 修正 `normalize_book_map`

- 接受 `支撐` 作為 `支柱` 的別名（別名表放 domain）。
- 定位到的卡少於 80% 就回傳 None。這會改變現有測試 `test_one_placed_card_is_enough_to_count_as_a_map` 與 `test_unknown_role_falls_back_to_case`，這是刻意的：做圖工具也因此不再快取壓平的地圖。
- 看板流程必須以 **Notion page id** 對應卡片。現有回傳值以標題為鍵，同名卡會共用一筆（CLAUDE.md 已登記的小債），這對做圖只是小地圖不準，對連結會寫錯頁面。

### 5. 寫入規則：只填空白

一本書**有任何卡的 `角色` 是空的**才處理，否則完全跳過、不呼叫模型。這些卡稱為「新卡」；第一次跑時全部都是。

- `角色`、`閱讀順序`：只填空白的。
- `相關卡片`：只寫**至少一端是新卡**的連結，兩端都寫，且與既有值取聯集，絕不移除。所以使用者刪掉的舊連結不會被加回來。
- 兩端都寫是刻意的：單一欄位的自我關聯在 UI 會雙向顯示，但 API 寫入是否如此未驗證，兩端都寫在兩種情況下都正確。

所有欄位先算好再寫，每張卡一次 `pages.update`。中途中斷時，沒寫到的卡仍是空白，下次重跑會補上。

少於 3 張卡的書不跑模型：角色填「案例」，只排順序，沒有連結。

### 6. 看板

`NotionViewsClient` 新增建立看板的方法，名稱沿用 `本書卡片`：

- `type: board`；`group_by` 是 `角色`（select）；`sorts` 依 `閱讀順序` 遞增；`filter` 是 `來源` 包含本頁；`cover` 用 `page_cover`。
- 卡片上只顯示標題和 `閱讀順序`，其他欄位在此 view 隱藏（`configuration.properties[].visible = false`）。

放置規則：

- 只處理 `is_created_by_integration` 的書頁；手動頁完全不碰。
- `筆記圖` 段空白時直接建看板。`CompleteReadingListPageUseCase._ensure_card_gallery` 改為建看板，先確保欄位存在；還沒跑過工具的卡會出現在「沒有角色」那一欄。
- 既有頁面：只取代**名稱為 `本書卡片` 且類型為 gallery** 的 view。優先在同一個 linked database 新增看板 view（`POST /v1/views` 帶 `database_id`），再 `DELETE /v1/views/{gallery}`，這樣位置不變。段落裡有其他 view 一律不動，已有看板就跳過。

### 7. 工具入口

```
python tools/build_card_board.py --dry-run             # 只列出會處理的書、卡數、要取代的 gallery；不呼叫模型、不寫入
python tools/build_card_board.py --book 主控力          # 只處理書名含此字串的書
python tools/build_card_board.py                       # 全部
```

- 跟著 `main.py` 跑的話每本多 6 分鐘，所以是獨立工具，不進同步流程。
- 依序處理（模型只有一個、VRAM 8GB），沒有 `來源` 的卡略過並記 WARNING。結尾報告處理／跳過／失敗的書，有失敗時 exit code 非 0。
- 成本：每本約 6 分鐘，全部（約 26 本有卡片）約 2 到 4 小時。

### 8. 移除 📖

- `ZettelkastenCardRepository._build_children` 不再產生這個 callout，`tests/unit/test_chapter_reference.py` 相應調整。`chapter_reference` 與 `_clean_chapter_reference` 保留，本地 JSON 照舊。
- `legacy/` 路徑不改（已登記待退役）。
- 新增 `tools/remove_card_chapter_callouts.py [--dry-run]`：掃所有卡的頂層 block，刪除 icon 為 📖 的 callout，其他不動。`--dry-run` 列出每一張卡與 callout 文字，**使用者看過後才正式跑**。重跑是 no-op。
- 現況：《主控力》18 張只有 1 張還有這行，其他書還不清楚。章名之後仍可用 `來源劃線ID` 從 Kobo 查回。
